# Size In Tooltip — спецификация (уточнена по итогам исследования)

## Цель

Новый мод: дублировать размер области выделения (прямоугольника) в тултип рядом с курсором.

Для инструментов с прямоугольным выделением («Копать», «Разрушить», «Отменить» и т.д.): пока пользователь тянет выделение, в тултипе рядом с курсором выводится размер. Внутри самого прямоугольника игра уже показывает размер (например `15x4` / `60 (в клетках)`), но в некоторых случаях он не виден — слишком большое выделение или тултип загораживает надпись. Мод продублирует эту информацию прямо в тултип.

Желаемый вид тултипа:

```
КОМАНДА "КОПАТЬ"
15x4
60 (в клетках)
(иконка лкм) ПЕРЕТАЩИТЬ   (иконка пкм) НАЗАД
```

(В черновике была строка «РАЗМЕР:» — заголовок убран решением пользователя после ручного принятия в игре: хардкод RU создавал i18n-проблему в не-RU локализациях, а числовые строки и так локализуются игровым ключом.)

## Формат отображения

- `<W>x<H>` — размеры прямоугольника (ширина x высота).
- `<N> (в клетках)` — площадь в клетках.
- Позиция в тултипе: строки размера между заголовком команды и строкой подсказки по кнопкам мыши (без отдельного заголовка — решение пользователя, i18n).

## Границы (scope)

**Включено:**
- новый мод (отдельный проект в репозитории, свой `UserMod2`, сборка по шаблонам и инвариантам репозитория);
- инструменты с прямоугольным выделением — **все** инструменты, тянущие прямоугольник («Копать», «Разрушить», «Отменить» и остальные) — решение зафиксировано пользователем на этапе уточнения;
- строки размера в тултипе, обновляемые по мере изменения выделения.

**Исключено (пока не решено):**
- модификация самой надписи внутри прямоугольника (только дубль в тултип);
- настройки/переключатель формата и включения (в v1 решено не делать; можно добавить позже);
- инструменты без прямоугольного выделения.

## Подход (уточнён по итогам исследования, см. research.md)

**Как строится тултип** (проверено по декомпилированному коду):
- Все карточки инструментов собираются базовым классом `HoverTextConfiguration` (`Assembly-CSharp/HoverTextConfiguration.cs`): каждый кадр `UpdateHoverElements` → `BeginShadowBar` → `DrawTitle` (заголовок «КОМАНДА "КОПАТЬ"») → `DrawInstructions` (строка «(ЛКМ) ПЕРЕТАЩИТЬ (ПКМ) НАЗАД») → `EndShadowBar`. Пер-тул карточки (`DigToolHoverTextCard`, `CancelToolHoverTextCard`, …) лишь переопределяют `UpdateHoverElements`/`ConfigureTitle`, но вызывают те же общие `DrawTitle`/`DrawInstructions` — **один общий кодовый путь**.
- RU-строки живут в LocString-таблице игры (`STRINGS`), а не в C#: ключи `UI.TOOLS.*` (заголовок, «ПЕРЕТАЩИТЬ», «НАЗАД»).

**Источник данных размера** (проверено):
- Размер внутри прямоугольника считается в `DragTool.OnMouseMove` (ветка Box/Line): мировой прямоугольник → зажим по границам → snap к углам клеток → размер в метрах → `Vector2I(W, H)` в клетках (округление) → формат `UI.TOOLS.TOOL_AREA_FMT = "{0} x {1}\n{2} tiles"` (RU «15x4» / «60 (в клетках)») → рисуется мировым текстом `areaVisualizerText` (создаётся при нажатии ЛКМ, удаляется при отпускании).
- Состояние прямоугольника в `DragTool`: `dragging` (public `Dragging`), `downPos`, `areaVisualizerSpriteRenderer.size` (размер в метрах), `mode` (Brush/Box/Line).

**Патч (один общий крюк для всех drag-инструментов):**
- Harmony **prefix** на `HoverTextConfiguration.DrawInstructions` (альтернатива — postfix на `DrawTitle`): поскольку все карточки вызывают этот общий метод, один патч покрывает все drag-инструменты.
- Условие: на GameObject карточки есть `DragTool`, и `dragTool.Dragging == true` (и режим ≠ Brush) → перед строкой с кнопками мыши рисовать строки размера (без заголовка «РАЗМЕР:» — решение пользователя после принятия в игре).
- W/H и N — из того же состояния, что и игра: `areaVisualizerSpriteRenderer.size` (метры) → округление до клеток (как в `DragTool.OnMouseMove`); строки форматируются игровым ключом `UI.TOOLS.TOOL_AREA_FMT` (автолокализация, цифры всегда совпадают с надписью внутри прямоугольника). Заголовок «РАЗМЕР:» удалён решением пользователя после принятия в игре — хардкода RU в моде не остаётся.
- Методы игры становятся public в публицизированном ассембле (BepInEx.AssemblyPublicizer, `Publicize=true`) — патч пишется в чистом C#; приватные поля читаются через рефлексию.

**Проект мода:**
- Новый проект `SizeInTooltip/`, клонированный со структуры `BuildDoorOverWall` (единственный референс в репозитории; `UpdatedOniTemplate/` в чекауте отсутствует): csproj (net48, `IsMod=true`, `IsPacked=true`, `ProjectReference` на `UtilLibs`), подкласс `UserMod2` с программным `harmony.Patch(...)`, README; добавление в `ONI-mods.sln` (строка `Project(` + 4 строки конфигураций; комментарии в sln запрещены MSBuild).

## Открытые вопросы (статус после исследования и ревью)

1. ~~Точный список инструментов~~ — **решено:** все инструменты с прямоугольным выделением.
2. ~~Ориентация~~ — **решено исследованием:** игра показывает W = округлённая ширина по X, H = округлённая высота по Y (формат `"{0} x {1}"`); мод берёт те же значения — цифры всегда совпадают с надписью внутри прямоугольника.
3. ~~`60 (в клетках)`~~ — **решено исследованием:** всегда `W*H` (игра не учитывает «занятые» клетки); мод делает то же.
4. ~~Когда показывать~~ — **решено исследованием:** только во время перетаскивания (`DragTool.dragging == true`) — прямоугольник существует только в момент драга (создаётся при нажатии ЛКМ, удаляется при отпускании); «зафиксированного выделения» у этих инструментов нет.
5. ~~Переключатель~~ — **решено:** в v1 нет UI настроек — блок всегда включён; можно добавить позже.
6. ~~Локализация~~ — **решено:** числовые строки идут через игровой LocString-ключ `UI.TOOLS.TOOL_AREA_FMT` (автолокализация); заголовок «РАЗМЕР:» убран решением пользователя после принятия в игре — хардкода RU в моде больше нет, i18n-проблем нет.

## Риски

- ~~Тултип может формироваться не централизованно~~ — **снят** исследованием: один общий базовый путь (`DrawTitle`/`DrawInstructions`), все карточки его вызывают — достаточно одного патча.
- Рефлексия в приватные поля `DragTool` (`areaVisualizerSpriteRenderer.size`, `mode`) — хрупко при обновлениях игры (поля могут переименовать); митигация — доступ через публицизированный ассемблер там, где возможно, и защитные null-проверки (мод не должен ронять игру).
- `UpdatedOniTemplate/` отсутствует в чекауте — проект создаётся клонированием `BuildDoorOverWall` (структура полностью задокументирована в research.md).
- Принятие — только ручной прогон игры пользователем; успешная сборка не доказывает работоспособность.
